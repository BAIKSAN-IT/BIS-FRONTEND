# 📦 Project Structure

본 프로젝트는 **React + TypeScript 기반 프론트엔드 프로젝트**이며,  
패키지 매니저는 **Yarn**을 사용합니다.

- 루트 디렉토리에서 무엇을 관리하는지
- 실제 개발 코드는 어디에서 작업하는지
- 화면이 어떤 흐름으로 동작하는지
- 공통 컴포넌트 / 상태관리 / 라우팅 / 타입 / 설정 파일이 어디에서 관리되는지
- 신규 화면이나 기능을 추가할 때 어떤 순서로 보면 되는지

---

## 📁 Root Project Structure

```bash
pis-frontend
├── .idea
├── node_modules
├── public
├── src
├── .editorconfig
├── .env
├── .env.development
├── .env.production
├── .gitignore
├── craco.config.js
├── package.json
├── yarn.lock
└── README.md
```

---

## 📂 Root Directory / File Description

### `.idea`
IntelliJ IDEA / WebStorm 계열 IDE에서 사용하는 프로젝트 설정 디렉토리입니다.

주요 내용:
- 프로젝트 SDK 설정
- 실행 / 디버그 설정
- 코드 스타일 설정
- IDE 내부 설정 파일

참고:
- 애플리케이션 실행 로직과 직접적인 관련은 없습니다.
- 개인 개발 환경 정보가 포함될 수 있습니다.
- 팀 공통 관리 대상이 아닌 경우도 많습니다.

즉, **JetBrains 계열 IDE 전용 설정 파일 모음**입니다.

---

### `node_modules`
Yarn으로 설치한 모든 외부 라이브러리가 저장되는 디렉토리입니다.

주요 역할:
- React, React DOM, TypeScript, Redux, React Router 등 외부 패키지 저장
- `package.json`에 정의된 dependency 실제 설치 위치
- 개발 및 빌드 시 필요한 라이브러리 제공

참고:
- 직접 수정하는 폴더는 아닙니다.
- `yarn install` 실행 시 자동 생성됩니다.
- 용량이 크기 때문에 일반적으로 Git에는 포함하지 않습니다.

즉, **프로젝트 실행과 빌드에 필요한 외부 라이브러리들이 실제로 들어 있는 디렉토리**입니다.

---

### `public`
정적 파일(static file)을 관리하는 디렉토리입니다.

주요 내용:
- `index.html`
- favicon
- 브라우저에서 직접 참조하는 이미지
- 빌드 시 그대로 제공할 파일

특징:
- React 번들링 대상이 아닌 파일이 위치합니다.
- 최초 브라우저 진입 시 사용하는 HTML 템플릿도 여기에 위치합니다.
- 정적으로 접근 가능한 파일을 둘 때 사용합니다.

예:
- `public/index.html`
- `public/favicon.ico`
- `public/logo192.png`

즉, **앱 실행 시 정적으로 제공되는 리소스를 보관하는 영역**입니다.

---

### `src`
실제 프론트엔드 애플리케이션 코드가 위치하는 핵심 디렉토리입니다.

주요 작업:
- 화면(Page) 개발
- 공통 컴포넌트 작성
- 상태관리 로직 작성
- 라우팅 정의
- 타입 정의
- 유틸 함수 작성
- 다국어 설정
- API 호출 흐름 구성

즉, **개발자는 대부분 이 디렉토리에서 작업합니다.**

---

### `.editorconfig`
코드 스타일을 통일하기 위한 설정 파일입니다.

주요 역할:
- 들여쓰기 방식 통일
- 줄바꿈 규칙 통일
- 파일 인코딩 설정
- 여러 개발자가 다른 에디터를 사용해도 기본 포맷 유지

즉, **팀 내 코드 작성 스타일을 최대한 통일하기 위한 설정 파일**입니다.

---

### `.env`
공통 환경변수 설정 파일입니다.

예:
- API Base URL
- 공통 환경 설정값
- 프로젝트 실행 시 필요한 변수

특징:
- 개발 / 운영 환경과 무관하게 공통으로 사용할 수 있는 값이 위치할 수 있습니다.
- 민감한 값이나 환경별 분기값을 코드 내부가 아닌 외부 파일로 분리할 때 사용합니다.

즉, **환경에 따라 바뀔 수 있는 설정값을 코드 밖에서 관리하기 위한 파일**입니다.

---

### `.env.development`
개발 환경용 환경변수 파일입니다.

예:
- 개발 서버 API 주소
- 로컬 개발용 옵션
- 테스트용 설정값

즉, **개발 환경에서 실행할 때 적용되는 환경변수 파일**입니다.

---

### `.env.production`
운영 환경용 환경변수 파일입니다.

예:
- 운영 서버 API 주소
- 운영 배포 기준 옵션
- 운영 환경 전용 설정값

즉, **배포 환경에서 적용되는 환경변수 파일**입니다.

---

### `.gitignore`
Git에 포함하지 않을 파일 및 디렉토리를 정의하는 파일입니다.

일반적으로 제외하는 항목:
- `node_modules/`
- build 결과물
- IDE 설정 파일
- 로그 파일
- 개인별 환경 파일

즉, **버전 관리 대상에서 제외할 파일을 정의하는 역할**입니다.

---

### `craco.config.js`
CRA(Create React App) 기반 설정을 커스터마이징하기 위한 파일입니다.

주요 역할:
- webpack 설정 수정
- alias 설정
- babel 설정 보완
- 기본 CRA 설정 확장

사용 이유:
- 기본 CRA 설정만으로 부족한 부분을 보완하기 위해 사용
- eject 없이 설정을 확장할 수 있음

즉, **기본 React 빌드 설정을 프로젝트 요구사항에 맞게 확장하는 파일**입니다.

---

### `package.json`
Yarn / Node 프로젝트의 핵심 설정 파일입니다.

주요 관리 항목:
- 프로젝트 이름 및 버전
- dependency / devDependency
- 실행 스크립트
- 빌드 / 테스트 관련 명령

예:
- `yarn start`
- `yarn build`
- `yarn test`

대표적으로 확인할 수 있는 항목:
- 어떤 라이브러리를 사용하는지
- 어떤 명령어로 앱을 실행하는지
- 어떤 빌드 툴 구성을 사용하는지

즉, **프로젝트가 어떤 라이브러리를 사용하고 어떤 명령으로 실행되는지 정의하는 파일**입니다.

프로젝트 구조를 파악할 때 가장 먼저 확인하는 파일 중 하나입니다.

---

### `yarn.lock`
Yarn이 설치한 라이브러리의 정확한 버전 정보를 고정하는 파일입니다.

주요 역할:
- 팀원 간 동일한 dependency 버전 유지
- 설치 결과 일관성 확보
- 개발 환경 / 배포 환경 차이 최소화

즉, **라이브러리 버전을 고정하여 설치 결과를 안정적으로 맞춰주는 파일**입니다.

---

### `README.md`
프로젝트 구조 및 사용 방법을 설명하는 문서입니다.

주요 내용:
- 프로젝트 개요
- 실행 방법
- 폴더 구조 설명
- 개발 시 참고 사항
- 신규 인원 온보딩용 안내

즉, **신규 인원이 가장 먼저 참고해야 하는 프로젝트 안내 문서**입니다.

## 📂 Source Directory / File Description

### `assets`
이미지, 아이콘, 폰트 등 정적 리소스를 관리하는 디렉토리입니다.

예:
- 이미지 파일
- 아이콘 파일
- SVG
- 폰트 파일
- 로고 파일

주요 목적:
- 화면에서 공통으로 사용하는 시각 리소스 관리
- 프로젝트 브랜딩 요소 보관
- UI 구성에 필요한 리소스 분리

즉, **화면에서 사용하는 시각적 리소스 파일 모음**입니다.

---

### `components`
여러 화면에서 공통으로 사용하는 UI 컴포넌트를 관리하는 디렉토리입니다.

예:
- 버튼
- 테이블
- 모달
- 입력 컴포넌트
- 차트 컴포넌트
- 카드 / 패널 UI
- 로딩 컴포넌트
- 공통 알림창

목적:
- 중복 코드 제거
- UI 일관성 유지
- 재사용성 향상
- 유지보수 편의성 확보

실무적으로는:
- 특정 페이지 전용으로만 쓰는 화면 조각은 `pages` 내부에 둘 수도 있음
- 여러 페이지에서 같이 쓰는 UI는 `components`로 분리하는 것이 좋음

즉, **화면을 구성하는 공통 부품을 모아두는 영역**입니다.

---

### `constants`
프로젝트 전체에서 공통으로 사용하는 상수값을 관리하는 디렉토리입니다.

예:
- 메뉴 코드
- 상태값
- 권한 코드
- 화면 구분값
- 공통 문자열 키
- 기본 설정값

장점:
- 하드코딩 감소
- 오타 방지
- 유지보수 편의성 증가

즉, **여러 곳에서 반복해서 사용하는 고정값을 관리하는 영역**입니다.

---

### `helpers`
기능 수행을 도와주는 보조 로직을 관리하는 디렉토리입니다.

예:
- API 처리 보조 로직
- 인증 관련 로직
- 파일 다운로드 보조 처리
- 특정 기능 흐름 지원 함수

`utils`와 차이:
- `utils`는 범용 함수 성격이 강함
- `helpers`는 기능 흐름 보조 성격이 강한 경우가 많음

즉, **화면 로직과 유틸 함수 사이에서 기능 흐름을 보조하는 영역**입니다.

---

### `hooks`
React의 커스텀 훅(custom hook)을 관리하는 디렉토리입니다.

예:
- 입력 상태 관리 훅
- 공통 ref 관리 훅
- API 상태 처리 훅
- 권한 확인 훅
- 공통 이벤트 처리 훅

장점:
- UI와 로직 분리
- 반복 로직 재사용
- 코드 가독성 향상
- 상태 관리 패턴 통일

즉, **React 공통 로직을 재사용 가능한 형태로 분리한 영역**입니다.

---

### `layouts`
페이지 전체의 공통 레이아웃을 관리하는 디렉토리입니다.

예:
- 메인 레이아웃
- 로그인 레이아웃
- 태블릿 전용 레이아웃
- 특정 도메인 전용 레이아웃

보통 포함되는 요소:
- Header
- Sidebar
- Footer
- Content Wrapper
- Layout Frame

목적:
- 여러 화면이 동일한 외형 구조를 공유할 수 있도록 구성
- 본문만 바뀌고 나머지 틀은 유지하도록 설계

즉, **여러 화면을 감싸는 공통 틀을 관리하는 영역**입니다.

---

### `locales`
다국어(i18n) 리소스를 관리하는 디렉토리입니다.

예:
- 한국어 번역 파일
- 영어 번역 파일
- 공통 문구 key/value 구조

목적:
- 언어별 문구 분리
- 하드코딩된 UI 텍스트 최소화
- 다국어 확장성 확보

즉, **다국어 문구를 언어별로 관리하는 영역**입니다.

---

### `pages`
실제 화면 단위의 컴포넌트를 관리하는 디렉토리입니다.

여기에는 사용자가 직접 보게 되는 페이지가 위치합니다.

예:
- 로그인 화면
- 대시보드 화면
- 목록 / 상세 화면
- 업무별 관리 화면
- 도메인별 메인 화면

핵심 개념:
- `components`는 공통 부품
- `pages`는 실제 화면

즉, **실제 업무 화면이 위치하는 핵심 디렉토리**입니다.

---

### `redux`
전역 상태 관리를 담당하는 디렉토리입니다.

주요 역할:
- 공통 상태 저장
- 비동기 요청 결과 저장
- 여러 화면에서 공유하는 데이터 관리

예:
- 로그인 사용자 정보
- 공통 코드
- 대시보드 데이터
- 전역 로딩 상태
- 선택된 필터 상태

구성될 수 있는 항목:
- store
- slice
- reducer
- async thunk
- action

즉, **애플리케이션 전체에서 공유하는 상태를 관리하는 영역**입니다.

---

### `routes`
라우팅 설정을 관리하는 디렉토리입니다.

주요 역할:
- URL과 페이지 연결
- 접근 권한 분기
- 로그인 여부에 따른 진입 제어
- 레이아웃별 라우트 분리
- 인증/비인증 라우트 구성

예:
- `/login`
- `/dashboard`
- `/mainfactory`
- `/srs/service`

즉, **어떤 주소로 들어왔을 때 어떤 화면을 보여줄지 정의하는 영역**입니다.

---

### `types`
TypeScript 타입 정의를 관리하는 디렉토리입니다.

예:
- API 요청 타입
- API 응답 타입
- 화면 데이터 타입
- 공통 객체 타입
- 테이블 Row 타입
- 공통 Props 타입

장점:
- 데이터 구조 명확화
- 자동완성 강화
- 런타임 이전 오류 예방
- 협업 시 데이터 형태 공유 가능

즉, **프로젝트에서 사용하는 데이터 구조를 명확하게 정의하는 영역**입니다.

---

### `utils`
범용적으로 자주 사용하는 유틸리티 함수를 관리하는 디렉토리입니다.

예:
- 날짜 포맷 함수
- 숫자 포맷 함수
- 문자열 정리 함수
- 퍼센트 계산 함수
- null / undefined 방어 처리
- 공통 계산 로직

즉, **여러 영역에서 공통으로 사용하는 순수 함수 모음**입니다.

---

### `App.css`
애플리케이션 전반에 적용되는 기본 스타일 파일입니다.

역할:
- 공통 스타일 정의
- 전역 스타일 적용
- 루트 컴포넌트 스타일 관리

## 🔄 Typical Frontend Flow

일반적인 프론트엔드 실행 흐름은 아래와 같습니다.

```text
Browser
  ↓
index.tsx
  ↓
App.tsx
  ↓
Routes
  ↓
Page
  ↓
Components / Hooks / Redux / Utils
```

즉, 브라우저가 앱에 진입하면:

1. `index.tsx`에서 React 앱이 시작되고
2. `App.tsx`가 전체 구조를 잡고
3. `routes`가 현재 URL에 맞는 페이지를 찾고
4. 해당 `pages` 화면이 렌더링되며
5. 필요 시 `components`, `redux`, `hooks`, `utils` 등을 사용합니다.

## 🔄 Typical Data Flow

일반적인 화면 데이터 흐름은 아래와 같습니다.

```text
User Action
  ↓
Page
  ↓
Hook / Handler
  ↓
API Call / Helper
  ↓
Response Data
  ↓
Redux or Local State
  ↓
Component Render
```

예를 들면:
1. 사용자가 조회 버튼 클릭
2. 페이지에서 조회 함수 실행
3. API 호출
4. 서버 응답 수신
5. 응답 데이터를 state 또는 redux에 저장
6. 테이블 / 차트 / 카드에 반영

즉, **사용자 액션 → 데이터 요청 → 상태 저장 → 화면 반영** 흐름으로 이해하면 됩니다.

## 🔐 Route / Auth Flow

인증이 필요한 화면에서는 일반적으로 아래와 같은 흐름을 가집니다.

```text
Request URL
  ↓
Route Check
  ├─ 로그인 여부 확인
  ├─ 권한 확인
  └─ 허용된 경우 Page 진입
  ↓
Layout 적용
  ↓
Page Render
```

예:
- 로그인하지 않은 상태에서 보호된 페이지 접근
- 로그인 페이지로 리다이렉트
- 로그인 성공 후 원래 접근하려던 페이지로 이동

즉, **라우팅 계층에서 접근 제어와 화면 진입 조건을 처리하는 구조**를 가질 수 있습니다.

## 🔄 Typical Development Flow

일반적인 개발 흐름은 아래와 같습니다.

1. `src/pages`에서 기능 화면 개발
2. 공통 UI가 필요하면 `src/components`에 분리
3. 타입이 필요하면 `src/types`에 정의
4. 공통 로직이 필요하면 `src/hooks`, `src/helpers`, `src/utils`에 작성
5. 전역 상태가 필요하면 `src/redux`에 추가
6. 라우팅이 필요하면 `src/routes`에 등록
7. 필요한 라이브러리를 `package.json`에 추가 후 `yarn install`
8. `yarn start`로 개발 서버 실행
9. `yarn build`로 배포용 빌드 생성

즉, **화면 / 공통 UI / 상태 / 라우팅 / 타입 / 유틸이 함께 맞물려 기능 하나가 완성되는 구조**입니다.
